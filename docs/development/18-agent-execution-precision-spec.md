## 2. 阶段目标

减少 Agent 将“可见但非阻塞”的输出误判为必须修复的问题，以及在缺少父目录或目标文件事实时进行可预防写入所造成的无效工具调用。改进必须建立在现有六个工具、结构化 `ToolResult` 和写入安全边界上，不通过隐藏 warning、自动创建目录或放宽覆盖校验来制造成功。

## 3. 只读观察范围与证据

本轮只读核对了阶段 17 R6 的真实事件结论、现有 System Prompt、六工具定义、`write_file`/原子写实现及其单元测试。没有修改业务代码或真实用户项目。

### 3.1 warning 误判事实

1. `run_process` 已以 `exitCode === 0` 和 readiness 状态决定结构化成功，stdout 与 stderr 只作为原始输出通道保存；成功命令可以包含 stderr warning。
2. R6 的一次失败 build 同时出现 TypeScript `TS2352` 阻塞错误与 Turbopack tracing warning。Agent 将两者都描述为“构建问题”并修改对应代码。
3. 随后的真实事件和独立复核均证明 build 在保留 tracing warning 时退出码为 0；因此该 warning 不是项目无法构建的直接原因。
4. 当前缺口主要位于模型可见行为契约：现有提示词强调修复错误和验证，但没有明确声明“stderr 是通道，不是严重级别”，也没有规定混合输出的因果收敛方式。

结论：不应修改 `run_process` 的成功判定，也不应按生态或字符串维护 warning 解析器；应让 Agent 以结构化结果为事实，在失败输出中只处理导致失败的直接原因。

### 3.2 `write_file` 失败事实

R6 共记录 9 次失败的 `write_file`：

| 原因 | 次数 | 可预防路径 |
| --- | ---: | --- |
| `parent_not_found` | 4 | 先确认父目录；缺失时显式创建后再写入 |
| `invalid_expected_hash_semantics` | 4 | 既有目标先读取最新 SHA；不存在目标才省略 SHA |
| 一般参数校验失败 | 1 | 按工具 Schema 生成完整合法参数 |

现有实现已正确拒绝以下危险或含混操作：

- 父目录不存在时不隐式创建目录。
- 覆盖既有文件时必须提供此前读取到的完整 SHA-256。
- 新建文件时不得伪造 `expectedSha256`。
- 写入前仍执行工作区、真实父目录和符号链接边界检查，并使用原子更新。

成功对照轨迹均遵循同一模式：检查父目录与目标；父目录缺失时先显式创建；目标存在时先 `read_file` 获取最新 SHA；目标不存在时才无 SHA 创建。当前工具说明和 System Prompt 分散提到依赖顺序与覆盖 SHA，但没有形成写入前必须执行的判定流程。

结论：运行时拒绝是必要的最后防线，不应改为自动纠错；缺口应在模型行为契约和工具说明中修复。

## 5. 设计规格

### 5.1 命令结果与 warning 的因果判定

Agent 必须按以下优先级解释 `run_process`：

1. `ToolResult.ok`、结构化 `error`、`metadata.exitCode` 和 readiness 字段是命令结果的权威事实。
2. stdout/stderr 是输出通道，不代表 success/error 严重级别；stderr 中出现 warning 不能单独推翻 `ok: true` 或退出码 0。
3. 当命令成功且满足当前验收要求时，Agent应记录必要 warning 并继续，不得仅为消除 warning 修改文件或扩大任务范围。
4. 当命令失败且同时包含阻塞错误与 warning 时，Agent只修复能够解释非零退出、readiness 失败或明确验收失败的直接原因，然后重跑原验证。
5. 重跑成功后应停止该失败恢复分支；仍存在但不阻塞的 warning 只在最终总结中如实报告。
6. 只有以下情况可主动处理 warning：用户明确要求零 warning；warning 本身违反已批准验收标准；或工具配置把 warning 明确提升为失败并导致结构化非成功结果。
7. 无法证明因果关系时，先做最小只读诊断；不得把相关性、同一输出块或 stderr 通道当作因果证明。

该规则不禁止修复真正的问题，也不宣称所有 warning 都安全；它要求用当前任务的结构化结果和验收标准决定是否行动。

### 5.2 `write_file` 前置观察决策流

每次写入前，Agent 必须使用同一 run 中仍然新鲜且覆盖当前路径的事实，或执行最小只读观察：

```text
准备 write_file
  → 是否已有当前父目录的可靠事实？
      ├─ 否：list_directory 父目录或最近存在的祖先
      └─ 是：复用事实
  → 父目录是否存在？
      ├─ 否：按既有风险规则显式创建父目录，再确认成功
      └─ 是：继续
  → 目标是否存在？
      ├─ 是：read_file 取得最新完整 SHA-256
      │       → write_file(path, content, expectedSha256)
      └─ 否：write_file(path, content)，不传 expectedSha256
```

补充约束：

- `read_file` 不是“探测不存在文件”的默认工具。对新文件应先从父目录 listing 判断不存在，避免把预期的 `not_found` 从写工具转移到读工具。
- 同一父目录下的批量新建可共享一次新鲜 listing；每个已存在目标仍需在覆盖前取得其最新完整 SHA。
- Agent 在本 run 中刚成功创建的目录或文件可以作为新鲜事实复用；发生可能改变目标的进程、外部审批等待、写入冲突或其他不确定变化后，应重新观察。
- `replace_in_file` 继续遵守其独立的读取与唯一匹配契约；本阶段不改变其接口。
- 显式创建目录继续通过现有 `run_process` 路径并接受既有风险评估和审批，不获得隐式授权。

### 5.3 模型可见内容与版本

- 固定自然语言继续全部使用简体中文，工具名、字段名、路径、哈希和原始输出保持原样。
- 新 System Prompt 版本必须在版本常量、请求捕获测试和文档中一致，不在运行时按 provider 分叉。
- normal 与 executing 获得完整执行规则；planning 虽不能写入或运行进程，仍应看到足够的依赖计划规则，以生成可执行且顺序正确的计划。
- 工具描述只解释事实与正确调用前置，不承诺工具会自动完成未显式调用的观察或目录创建。

## 6. 错误、安全与兼容性

1. 现有 `parent_not_found`、`invalid_expected_hash_semantics`、`FILE_CHANGED` 等拒绝继续保留，作为模型偏离契约、并发变化和恶意参数的确定性防线。
2. 如果新鲜观察后仍因并发变化写入失败，Agent 必须重新读取/观察并重新判断；不得复用陈旧 SHA 或删除并发保护。
3. 任何写入、目录创建和命令仍受工作区边界、符号链接检查、风险审批、取消、预算和总时限约束。
4. 不改写旧 JSONL，不增加恢复迁移；旧 run 的输出和失败语义保持原样。
5. 提示词和工具描述变化会影响模型行为但不改变 ToolResult Schema、HTTP、Client 或 UI 协议。
6. 真实输出可能包含秘密或绝对路径；测试只使用脱敏 fixture，文档不复制真实凭据或不必要的完整日志。

## 8. 验收标准

| ID | 验收标准 |
| --- | --- |
| AC18-01 | 对 `ok: true`、退出码 0 且 stderr 含 warning 的命令，确定性 Agent 将其视为成功，不产生仅用于消除 warning 的写工具调用，并在需要时如实报告 warning。 |

| AC18-05 | normal、planning、executing 及 DeepSeek/LongCat/Generic 使用同一版本化中文契约；原始 stdout/stderr、路径、工具名和字段名不被翻译或改写。 |

## 9. 测试策略

### 9.1 红灯优先的确定性测试

- 请求捕获：断言新版本提示词与四个相关工具描述在三 phase 中可见且中文合规。
- warning 成功轨迹：假模型收到退出码 0 和 stderr warning 后直接继续验证或总结，零非必要写入。
- 混合失败轨迹：第一次非零输出含 blocker 与 warning，只修改 blocker；第二次退出 0 后结束恢复。
- 写入轨迹：覆盖缺失父目录、新文件、既有文件、同目录批量文件、刚创建事实复用与并发 SHA 变化。
- 安全回归：模型直接跳过观察时，现有工具仍结构化拒绝；planning phase 仍无法执行写入或目录创建。

测试不得依赖真实模型对自然语言的概率理解来证明核心契约；真实 LongCat 只作为独立的窄范围回归证据。

### 9.2 验证顺序

Task 阶段应明确最小相关测试、跨层专项和全量门禁的顺序。任何失败都须记录原始症状、根因、修正和完整重跑结果，不得降低断言、删除测试或把 warning 隐藏为通过。
