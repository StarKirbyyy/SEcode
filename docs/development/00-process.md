# 阶段开发与三级审批门禁规范

## 1. 目的

SEcode 采用观察驱动、文档先行和用户逐步审批的开发方式。任何阶段都不得从想法直接进入编码；先确认事实与规格，再确认任务，最后实现并提交总结。

本规范自用户批准后生效。阶段 01、02 在本次修订前已经完成或进入总结审阅，不追溯伪造此前不存在的审批记录；从阶段 03 起严格执行全部三级门禁。

## 2. 每个阶段的固定生命周期

每个阶段必须依次经过三个子阶段，任何一步未获用户明确批准都必须停止。

```text
只读观察
  → Spec 文档
  → 用户审批 Spec
  → Task 文档
  → 用户审批 Task
  → 实际开发与验证
  → Summary 文档
  → 用户审批 Summary
  → 阶段正式完成
```

### 2.1 观察与 Spec

阶段开始时先执行一次只读观察，允许：

- 阅读已经批准的需求、规格、任务和总结文档。
- 检查当前代码、配置、依赖、测试、Git 状态和运行环境。
- 执行不会修改受版本控制文件的诊断、测试或构建。
- 识别现状、缺口、风险、依赖关系和待确认设计决策。

观察阶段禁止：

- 编写业务代码。
- 安装或删除依赖。
- 修改配置或执行会重写文件的命令。
- 提前创建后续 Task 或 Summary 文档。

观察完成后生成 `NN-topic-spec.md`，至少包含：

- 阶段目标与需求 ID。
- 观察范围、观察方法和事实证据。
- 当前实现状态与差距。
- 范围内、范围外。
- 建议设计、接口、数据流和错误模型。
- 安全与兼容性约束。
- 可测试的验收标准。
- 风险、假设和待用户确认项。
- Spec 审批状态。

生成 Spec 后立即停止。只有用户明确回复“阶段 NN Spec 通过”或语义等价的批准，才能整理 Task 文档。

### 2.2 任务拆分与 Task

Spec 获批后，根据已经批准的 Spec 生成 `NN-topic-tasks.md`。该步骤只允许修改任务文档，不允许实现业务代码。

Task 文档至少包含：

- 批准的 Spec 链接和审批记录。
- 按依赖顺序排列的任务清单。
- 每项任务的输入、输出、涉及模块和完成条件。
- 每项任务覆盖的需求与验收标准。
- 预期新增或修改的文件范围。
- 测试计划、失败处理和回退策略。
- 明确不执行的工作。
- Task 审批状态。

任务必须足够具体，使实现阶段不再需要临时决定公共接口或安全策略。

生成 Task 后立即停止。只有用户明确回复“阶段 NN Task 通过”或语义等价的批准，才能开始实际开发。

### 2.3 开发、验证与 Summary

Task 获批后，严格按任务顺序实施：

1. 开始任务前对照 Spec 和 Task。
2. 只修改任务允许的文件和行为。
3. 每完成一项任务立即执行对应的最小验证。
4. 失败时记录真实原因，再修复并完整重跑相关验证。
5. 所有任务完成后执行该阶段的整体验证和反思检查。

完成后生成 `NN-topic-summary.md`，至少包含：

- 批准的 Spec、Task 及审批记录。
- 实际完成的任务清单。
- 详细开发过程和关键实现说明。
- 实际新增、修改、删除的文件。
- 所有验证命令和结果。
- 失败、诊断、修正及重新验证记录。
- 与 Spec/Task 的偏差及原因。
- 安全检查、已知限制和遗留风险。
- 反思与下一阶段影响。
- Summary 内部门禁与用户审批状态。

生成 Summary 后立即停止。只有用户明确回复“阶段 NN Summary 通过”或语义等价的批准，阶段才正式完成，才能开始下一阶段的观察。

## 3. 文档命名与状态

从阶段 03 起，每阶段固定产生三份文档：

```text
docs/development/NN-topic-spec.md
docs/development/NN-topic-tasks.md
docs/development/NN-topic-summary.md
```

文档状态只能是：

- `草拟中`
- `待用户审批`
- `用户要求修订`
- `已批准`
- `被后续修订取代`

审批记录必须写入对应文档，包含审批结果和它解锁的下一步。不得将内部检查通过写成用户已批准。

## 4. 变更与重新审批规则

- 用户要求修订时，只修改当前等待审批的文档或产物，修订后重新等待批准。
- 开发中发现公共接口、安全边界、阶段范围或验收标准需要变化时，立即停止开发并回到 Spec 修订；原 Task 审批同时失效。
- 仅任务顺序、文件位置或局部实现细节变化，但仍在 Spec 内时，停止开发并修订 Task，重新等待 Task 批准。
- Summary 必须如实记录所有偏差，不能通过回写文档掩盖未经批准的设计变化。
- 不修改与当前批准任务无关的业务代码，不覆盖用户已有修改。

## 5. 安全与合规纪律

- 不提交 API Key、Token、Cookie、真实凭据或包含凭据的日志。
- 所有环境配置提供无秘密示例；真实值只进入被忽略的本地环境文件。
- 不使用题目禁止的 Agent 框架或服务端托管代码/文件工具。
- 测试失败时不得降低断言、跳过用例或删除测试来制造通过结果。
- 删除、覆盖、迁移和外部状态变更必须严格限制在已批准 Task 范围。
- 每个公共接口、安全策略和持久化格式必须先在 Spec 中批准。

## 6. 测试与终端优先策略

测试分为两个层次：

1. **阶段内最小验证**：类型、解析器、文件安全等纯模块在各自阶段立即用单元测试验证。
2. **Agent 完整行为验证**：必须先完成可交互终端入口，再通过终端人工测试和自动集成测试 Agent 全流程。

固定顺序：

```text
核心模块
  → Agent 状态机与上下文
  → 可交互终端入口
  → 终端中的真实任务测试与修正
  → Next.js API
  → 中文 Web UI
  → UI 端到端验收
```

约束：

- 在终端交互阶段完成前，不得开发 Web UI。
- Agent 的模型调用、工具循环、审批、取消、历史恢复必须先在终端中可观察和调试。
- UI 只消费已经通过终端验收的核心能力，不在 UI 层修补 Agent 业务逻辑。
- Playwright 页面基础设施测试可以保留，但完整产品 E2E 只能在 UI 阶段执行。

## 7. 通用内部门禁

Summary 提交用户审批前必须满足：

- [ ] Spec 和 Task 均有明确用户批准记录。
- [ ] 批准的任务清单全部完成。
- [ ] 实现与已批准 Spec、Task 一致。
- [ ] 本阶段要求的最小验证和整体验证全部通过。
- [ ] 所有失败与修正已如实记录。
- [ ] 无新引入的秘密、越界写入或未说明风险。
- [ ] 反思和下一阶段影响已记录。
- [ ] 开发索引状态已更新为“Summary 待审批”。

内部门禁通过不等于阶段完成。只有 Summary 获用户批准，才能开始下一阶段。
