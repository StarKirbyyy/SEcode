## 3. 只读观察与事实证据

### 3.1 计划内容完整持久化，但 UI 呈现错误

- 目标 Session 为 `c99e7435-233a-457a-9da7-d415ac946ccb`。序号 25 的 `plan.proposed` 在 23:25:39 已一次性持久化完整 1948 字符计划，说明模型、NDJSON durable 事件和 JSONL 存储没有截断。
- `PlanApproval` 当前用 `<pre><TypingText /></pre>` 显示计划，没有使用已有 `MarkdownMessage`，所以标题、表格、列表和代码围栏只能作为纯文本显示。
- `advanceTyping` 对每个动画帧分别执行 `floor(elapsedMs / 1000 × rate)`。在约 16.7ms、45 字符/秒时每帧增量恒为 0；首次 catch-up 只显示到 `total - ceil(0.25 × 45)`，因此最后约 12 个字形永久停留。
- 用户在 23:26:12 批准后，`item.approved !== undefined` 令 `flush=true`，尾部才一次性显示。这与用户看到“最后几个字批准后才出现”完全一致。
- 现有 typing 单元测试只验证 100ms 单步，没有覆盖连续 16ms 帧；Plan Mode E2E 只断言“实施计划”标题和按钮出现，没有断言长计划全文或 Markdown 语义。

### 3.2 后端端口失败来自宿主环境继承，不是代码缓存

- 首次生成的后端使用 `const PORT = process.env.PORT || 3000`。`run_process` 的 `filteredEnvironment()` 复制 SEcode 进程的全部非敏感环境，因此子进程继承了宿主 `PORT=3000`。
- Agent 把源码默认值改为 3001 后，三次启动仍监听 3000；读取文件已证明源码修改生效。原因是 JavaScript 的环境变量优先级，不是缓存。
- `RunProcessArgumentsSchema` 明确不支持自定义环境变量，并声明 `shell:false` 直接传参。真实模型仍尝试 `ps aux | grep node` 和 `echo PORT=$PORT`；前者把 `|` 当作 `ps` 参数失败，后者原样输出 `$PORT`。
- 下一 run 把变量改为 `SERVER_PORT || 3001` 后，service 在 116ms 内 readiness 成功，直接验证根因。
- System Prompt 要求 service + readiness 是正确的验收边界；浪费来自未公开的宿主 `PORT` 继承、不能覆盖环境的工具契约以及模型违反无 Shell 语义。独立危险工具审批放大了重复错误的墙钟成本，但不是端口冲突根因。

### 3.3 Agent 已观察空工作区，但没有按事实安排依赖顺序

- 规划阶段两次成功列出根目录为空，并搜索过 `AGENTS.md`；因此问题不是完全缺少观察。
- 计划获批后的第一批执行却是六个 `write_file`，目标父目录均不存在，六次全部返回 `WORKSPACE_PARENT_NOT_FOUND`；之后 Agent 才重新列根并执行 `mkdir -p`。
- System Prompt V6 和工具说明已经要求“父目录依赖按序执行”“新建目录先 list_directory”，但它们是软约束。当前 Runtime 没有利用本 run 的 fresh listing 事实阻止“已知父目录缺失仍批量写入”。
- 阶段 18 的相关集成测试使用预编排假模型直接给出正确顺序，只证明系统能执行正确轨迹，没有证明真实模型会自主选择该轨迹。真实运行因此推翻了“仅靠确定性轨迹即可验收 FR-024”的隐含假设。

## 4. 方案比较与选定方案

### 4.1 方案 A：只加强 System Prompt

- 优点：改动最小，无运行时状态。
- 缺点：V6 已包含相关规则，真实模型仍违反；继续增加文字无法形成确定性保证。
- 结论：不采用为唯一方案，只允许做必要的短句澄清。

### 4.2 方案 B：让 `write_file` 自动创建父目录

- 优点：空项目创建调用更少。
- 缺点：把显式目录创建变成隐式副作用，模糊审批与审计边界，削弱 `WORKSPACE_PARENT_NOT_FOUND` 的安全语义。
- 结论：不采用。

### 4.3 方案 C：呈现修复、项目端口规避、窄运行前校验与真实模型门禁

- 计划 durable 文本直接按 Markdown 完整显示；打字动画只用于真实 `assistant.delta`，并修正其连续帧计时。
- SEcode 默认使用 3000 端口；Agent 创建新项目时预先选择其他端口，并使用项目专用端口变量，避免继承的通用 `PORT` 把服务重新导向 3000。
- Runtime 维护当前 run 的最小观察事实，在执行 `write_file` 前识别“父目录已被 fresh listing 明确证明不存在”的调用，阻止其进入文件执行器并给出有限、可恢复的依赖诊断；目录仍必须通过显式、独立审批的进程调用创建。
- 增加与本次真实轨迹等价的长计划、3000 保留端口和空工作区真实模型回归。
- 结论：采用。它针对已证实的失败点，不新增工具、事件、依赖或隐式文件副作用。

## 5. 设计规格

### 5.1 Plan Mode 呈现

1. `plan.proposed` 是完整 durable 事实，进入客户端账本后必须立即显示全部 `content`，不得重新模拟流式生成。
2. 计划正文使用与 assistant 最终消息一致的安全 Markdown 渲染能力，支持标题、段落、列表、表格、行内代码和代码块；不得使用 `dangerouslySetInnerHTML`。
3. Plan 卡片保留独立的标题、状态和批准/拒绝按钮；Markdown 正文不改变审批 ID、同 run 继续和刷新恢复语义。
4. 打字效果只能消费真实 `assistant.delta`。durable `plan.proposed`、历史恢复和批准状态变化均不得启动或控制正文动画。
5. `TypingText` 对真实 delta 使用累计时间或等价的非丢失算法；连续约 16ms 帧最终必须推进到全文，不能因逐帧取整永久保留尾部。隐藏页面、减少动态效果、运行终态和 authoritative durable message 继续立即 flush。

### 5.2 新项目端口规避与无 Shell 契约

1. System Prompt 明确把 3000 视为 SEcode 本地 Web 服务的默认保留端口。Agent 创建新项目时不得把新后端、前端或其他长期服务的默认端口设置为 3000。
2. 新项目在写入配置前确定互不冲突的非 3000 高位端口；例如后端可用 3001、前端可用 5173，但最终端口仍须通过 service readiness 验证，不能仅因选了常见端口就宣称可用。
3. 新 Node.js 服务不得使用会被 SEcode 宿主继承值覆盖的通用 `process.env.PORT` 作为唯一配置。应使用项目专用变量名（例如 `SERVER_PORT`）与非 3000 默认值，并让后端监听、前端代理、README、API 检查和 readiness 使用同一事实。
4. 如果选定的非 3000 端口仍返回 `EADDRINUSE`，Agent 记录结构化失败，选择另一个非 3000 端口并一次性同步所有调用方；不得杀死未知端口进程，也不得反复只改 fallback 而忽略环境变量优先级。
5. 对用户已有项目不无条件改写其端口设计；只有当前任务需要启动且实际冲突时，才在授权范围内做最小一致修改并说明偏差。
6. 本阶段不改变 `run_process` 的环境继承，不新增任意 `env` 参数；现有秘密过滤、风险审批、取消、超时和进程组清理保持不变。
7. 工具说明和 System Prompt 用简短中文明确：`program` 与 `args` 直接传给 `spawn`，不解释 `|`、`&&`、重定向、`$VAR` 或命令替换。需要诊断时调用单一程序及其原生参数。

### 5.3 写入依赖事实与运行前校验

1. 每个 run 只维护完成当前判断所需的最小、内存态观察事实，不新增 durable 事件格式，也不把该事实跨 run 当作有效授权。
2. 成功的 `list_directory` 可证明返回目录存在，并证明其直接列举范围内未出现的目标/子目录当时不存在；成功的 `read_file` 证明目标文件存在并提供 SHA。
3. 计划阶段的只读事实可在同一 run 获批执行后复用；进程执行、审批等待、写入冲突或其他可能改变目录的动作后，按现有 V6 规则使相关事实失效或要求重查。
4. 若 fresh 事实已经证明 `write_file` 的父目录不存在，Runtime 在进入文件执行器前返回一个有限、可恢复的依赖错误，并抑制同一模型响应中依赖同一缺失父目录的其余写入，避免产生六个等价失败。
5. 该校验不得自动创建目录、自动批准 `mkdir`、猜测符号链接结果或绕过工作区真实父目录检查。父目录创建成功后，后续写入仍由 `write_file` 执行自身的真实路径与 SHA 安全校验。
6. System Prompt 明确空工作区顺序：观察根目录 → 显式创建所需目录 → 写新文件 → 安装/构建/service readiness；根 listing 已证明目录缺失时无需再对不存在路径做无效读取。

### 5.4 真实模型回归门禁

1. 确定性单元/集成测试继续验证边界和错误分支，但不再作为 FR-024 自主行为的唯一证据。
2. 在所有自动门禁通过并向用户展示结果后，必须获得一次独立明确批准，才能在全新带 marker 的临时工作区执行真实模型回归；本次 Spec 批准、Task 批准或工具审批均不能复用为该授权。
3. 真实任务覆盖：空工作区、Plan Mode、长 Markdown 计划、前后端目录创建、依赖安装、SEcode 已占用默认 3000 端口、后端与前端 service readiness，以及最终 API/页面检查。
4. 事件验收要求：计划批准前全文可见；首次写工具前所需父目录已显式创建；正常路径零 `WORKSPACE_PARENT_NOT_FOUND`；零无 Shell 管道/变量展开工具调用；服务实际端口与 readiness 一致。
5. 回归只操作新临时工作区，不读取或输出 API Key，不触碰真实用户项目，不初始化 Git，不自动批准危险工具；失败必须保留事件证据并如实进入 Summary。

## 6. 错误、安全与兼容性

- 不修改既有 JSONL、`plan.proposed`、`assistant.delta`、工具名或公开 API；旧 Session 刷新后直接使用新的完整 Markdown 计划呈现。
- 运行前依赖错误必须有限、中文、可恢复且不包含绝对路径、模型私有推理或完整目录内容；重复抑制只作用于当前模型响应中的同一已知缺失父目录。
- 端口规避不得读取或输出完整环境；测试只验证生成项目在宿主 `PORT=3000` 时仍使用已选非 3000 项目端口，不快照或泄露其他真实环境值。
- 不降低 `run_process` 风险审批，不允许 Shell，不自动终止占用端口的未知进程，不把本产品描述为恶意代码安全沙箱。
- 不新增第三方依赖，不新增工具，不引入 Agent 框架，不执行 Git 写操作。

## 8. 范围外

- 不重新设计通用 Markdown 引擎、富文本编辑器或任意 HTML 渲染。
- 不改变 `run_process` 环境继承，也不增加通用自定义环境、Shell、管道、重定向、交互 stdin 或系统进程管理能力。
- 不让 `write_file` 递归建目录，不新增专用 `mkdir` 工具，不改变六工具首版边界。
- 不保证模型永不生成错误调用；目标是让已知依赖错误在执行前可解释收口，并以真实模型门禁验证概率行为。
- 不修改用户在目标工作区生成的示例项目，不清理当前仍可能运行的外部服务，不提交、推送、发布或部署。
- 不在本阶段制作 README、视频或最终提交包；这些工作属于顺延后的阶段 20。
